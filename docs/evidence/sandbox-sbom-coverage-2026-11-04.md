# Sandbox SBOM coverage work

The previously proposed Syft 1.42.3 has a demonstrated JavaScript cataloger omission: it silently drops a `package.json` when plural `authors`, `contributors`, or `maintainers` is a scalar string or object. The upstream fix is [Syft PR 4779](https://github.com/anchore/syft/pull/4779); its merge commit is an ancestor of Syft 1.56.0. The release now pins Syft 1.56.0 by Linux archive SHA-256 and runs `scripts/check_syft_cataloger.py` against the actual installed binary. In a local real-binary check, 1.42.3 omitted all six synthetic scalar-field packages while 1.56.0 reported all six. This specific check is a regression gate, not a completeness proof. Independent review compared the older failed-run SBOM against the image's npm lock and found the 95 known installed entries by name and version; an actual omission in that image was not established.

`scripts/check_sbom_inventory.py` is an **offline scoped oracle prototype**, not a release qualification. It streams a caller-supplied merged-filesystem tar without extracting it and independently checks identities from:

- installed entries in `/var/lib/dpkg/status`, including Debian architecture;
- Python `*.dist-info/METADATA` under `site-packages` or `dist-packages`;
- package manifests at installed package roots under `/home/pentester/.npm-tools/node_modules`, `/usr/share/nodejs`, and `/usr/local/lib/node_modules`, including nested `node_modules` and safely resolved in-scope relative metadata symlinks.

It compares the identities with typed SPDX package URLs and reports missing and unresolved metadata. It intentionally fails on missing identities, duplicate critical metadata fields, invalid metadata, unsafe paths, unresolved links, oversized files, or absent ecosystem inventories. npm metadata-file symlinks are resolved only to in-scope tar entries with a bounded link depth; every other symlink and hardlink anywhere in the archive is conservatively unresolved because an arbitrary link could conceal a Python installation or package directory. This can cause an incomplete result even when links are benign. A successful result means only that the identity sets in those scopes matched: duplicate installations at different paths can collapse to one identity, the inputs are not authenticated or bound to a common image, and the tool does not validate evidence relationships, licenses, file checksums, or all package sources. In particular it does not independently inventory Go applications/modules, vendored or embedded code, distributions without Python dist-info, package metadata outside the listed npm roots, other package managers, or language/tool-specific packages not represented in those sources. It cannot prove that the SBOM contains every package or that Syft found all files.

The prototype accepts only uncompressed Docker-export tar streams. It independently checks block framing and header checksums, requires two complete zero end blocks followed only by zero padding, and rejects truncated records, concatenated archives, nonzero data after the end marker, PAX size overrides and sparse formats. This deliberately rejects some otherwise valid tar variants; it has not been qualified against the actual native release exports.

Processing fails closed after 64 GiB of archive input, one million archive entries, 64 Mi characters of aggregate archive paths and links, 256 MiB of aggregate selected metadata, 200,000 selected metadata records, 1,024 characters per package identity field, 4,096 characters per archive path, link or package URL, or 64 symlink hops. Archive entries are read with explicit `TarFile.next()` and the cached members are cleared on each iteration; local macOS tests cover CPython 3.9, 3.12 and 3.13. Linux behavior remains to be verified. Individual selected metadata files and the SBOM are limited to 32 MiB and 256 MiB respectively; tar extension headers are limited to 64 KiB and sparse tar entries are rejected. The CLI requires POSIX interval timers and sets a 900-second processing deadline, including blocked pipe input. Operating-system I/O that cannot be interrupted by a signal is outside that guarantee. The aggregate input is caller-supplied and no identity or completeness claim follows merely from remaining within these limits.

Each invocation requires a fresh output path and creates it exclusively with owner-only permissions before reading inputs. An existing file or symlink is never overwritten. A failed or interrupted fresh invocation can leave an empty or partial file; consumers must check the process exit status and use a unique output path for each invocation rather than reading an old path after an error.

A local streaming smoke read an **unstarted, existing non-release** amd64 image `sha256:8233203294f63dee305842334263037acaf7e9e4f75297b87ddfbf0267b3e688`, labelled engine revision `6ad29d0aedf89ddf4344b9dfc1d2a5bd86f9dba7`, against the unrelated original failed-run SBOM. An earlier version of the oracle reported 930 Debian, 174 Python and 1,735 npm identities with no missing or unresolved entries after resolving an in-scope lodash metadata symlink. That smoke preceded the stricter directory-link and duplicate-field checks and has not been repeated with them; it is not evidence that the current checks pass for that image. Because the filesystem and SBOM were not from the same immutable image, it is a parser and performance smoke only. The task-owned unstarted container was removed; no image was pulled or removed.

The workflow therefore contains an **unconditional hold before promotion**. To remove it, a subsequent reviewed change must bind each oracle input to the same qualified native manifest, obtain and retain actual amd64 and arm64 results, extend or independently qualify the excluded package categories and evidence needed for the claimed coverage, and complete independent review and hosted verification. Do not substitute this prototype's green result for that work.

## Image-bound qualification design and remaining evidence

On 2026-11-04 the local Docker image inventory contained the non-release amd64 candidate above, but no local LyraShield sandbox arm64 image or matched native release filesystem. Its local image/config ID and reported local repository digest are `sha256:8233203294f63dee305842334263037acaf7e9e4f75297b87ddfbf0267b3e688`; neither establishes the registry manifest bytes for the historical qualified image. The retained 53,616,371-byte historical SPDX document names a different index and runtime revision (`992b3d9df696753c7b62a31ea58f1ca5d21055c1`). The other retained platform SPDX files were generated for Alpine test images, not native LyraShield releases. No available pair is a qualifying two-platform release input.

A defensible future qualification needs both a verified byte chain and a defined coverage claim. One possible implementation is:

1. Independently verify the existing signed native-qualification and SBOM-binding attestations, including their trusted workflow, run/attempt, subject, source revisions and index bytes. Select each child from the verified index; hash the exact fetched child manifest bytes and require the expected digest and platform. Fetch each descriptor by digest, verify its declared size and digest, and verify the image configuration and ordered layer descriptors against that manifest. Check the configuration's platform and `rootfs.diff_ids` against the ordered **uncompressed** layer hashes; compressed layer descriptor hashes alone do not bind a caller-provided merged export.
2. Independently construct the merged filesystem from those verified layers using a reviewed, pinned implementation with bounded resource use and correct OCI whiteout, opaque-directory, link, duplicate-path, ownership and path traversal handling. The oracle must consume that constructed view directly, without executing image code. A runtime-based export could instead be used only with an explicitly trusted, isolated and validated runtime/exporter; the export's hash or image labels alone do not prove that its bytes came from the child manifest. The current caller-supplied tar checker implements neither reconstruction nor this trust bridge.
3. Hash the exact per-platform SPDX bytes and compare them with the verified signed binding; run independently implemented inventories over the same reconstructed view. Record exact input, implementation/version, policy, results and unresolved findings by architecture. Every mismatch, unsupported archive feature, missing required inventory or failure must block qualification. Preserve durable, digest-addressed results and sign the qualification from an approved workflow; a consumer must verify the signature, approved policy and all digest bindings independently before accepting it. Signing a report cannot repair a missing filesystem-to-manifest proof or prove an oracle's coverage by itself.
4. Test the construction and policy with independently generated fixtures: altered manifest/config/layer bytes, wrong architecture, reordered or substituted layers, wrong diff ID, whiteouts and opaque directories, links, duplicate names, malformed/truncated streams, resource exhaustion and mismatched SPDX/report, including false-green attempts. Qualify the exact implementation and full-size exports on both native architectures, exercise negative controls, retain results and perform an independent review before considering removal of the hold.

The coverage policy must account for actual image inputs, not infer completeness from the three prototype sets. The Dockerfile installs Debian, Python and npm packages, but also copies eight rebuilt Go applications and their receipts, installs four distro Go applications, clones three tools and eight tree-sitter repositories, clones nuclei templates, and installs a separately downloaded Caido binary. Go binaries can embed dependency graphs; installed Python/npm packages can vendor code; Debian ownership does not enumerate embedded components. `containers/verify_go_tool_provenance.py` verifies eight application binaries against builder receipts and reports their main coordinates, while the existing audit also examines four distro applications; neither proves that every embedded dependency, vendored component, downloaded binary, cloned source tree, or other package in the entire filesystem appears in the SPDX. Each category needs an explicit definition of the represented component, independent discovery and matching method, justified exclusions and negative controls. Unknown categories or unresolvable identities must block the defined claim rather than silently count as covered.

This is a qualification design, not an implemented or validated release gate. The current strict tar parser's handling of real OCI-derived rootfs streams, Linux execution, resource use on the 6.33 GB local candidate, complete category discovery, durable signed qualification, and both hosted platform runs remain unverified. No image was pulled, built, removed, or promoted during this investigation.
