# Publishing the sandbox image

The sandbox publisher builds one image on each native GitHub-hosted platform, rather than emulating ARM on the x86 runner. Each image must pass the existing sandbox smoke and Go application audits before it can contribute a digest. The final job assembles the two qualified digests, verifies the exact runnable child manifests, creates the SBOM and attestations, and only then moves the release tags. The final digest, not a tag, is the deployable reference.

A manual dispatch from `main` may select an optional **full 40-character engine commit** with `engine_revision`; leaving it empty selects the workflow commit. The only historical revision currently approved for explicit selection is `992b3d9df696753c7b62a31ea58f1ca5d21055c1`; adding another requires a reviewed workflow change and its own qualification. A `sandbox-v*` tag builds its own commit. The selected engine commit must be an ancestor of the dispatch/tag commit and have a successful, completed `Engine CI` push run on `main`. Both native jobs check out that exact revision and record it as the image revision label. Dispatching this newer workflow for the approved earlier engine revision does not change the engine source revision.

The normal GitHub provenance attestation identifies the **workflow revision**. A separate signed `https://lyrashieldai.com/attestations/sandbox-qualification/v1` predicate binds the selected engine revision, workflow revision, successful engine CI run and attempt, publisher run and attempt, both platform index and runnable manifest digests, and the assembled index digest. A consumer that accepts a historical engine revision must verify both attestations, the trusted signer and certificate run/attempt, the predicate's values and final subject, the exact reviewed workflow revision, and the successful native jobs for that same run. An image label or a caller-supplied predicate alone is not evidence of source or qualification.

A failed, cancelled or timed-out build leaves only uniquely named candidate artifacts; it does not qualify or promote a digest. An actual publish is qualified only when the complete workflow, both native jobs, index checks, audits and attestations have succeeded and the digest has been independently verified.

## Bounded SBOM coverage qualification

The publisher also evaluates a finite filesystem-to-SPDX claim for each native child. It verifies the qualified child manifest and config descriptors by digest, pulls and inspects the exact local image, records and rechecks the returned container ID, creates the container without starting it, and exports the unstarted container's merged root filesystem with a 900-second timeout and an 8 GiB byte cap. The gate hashes those exact bytes and checks the retrieved SPDX binding against the signed SBOM predicate.

One streaming pass inventories installed Debian identities in `var/lib/dpkg/status`, Python `*.dist-info/METADATA` under the declared `dist-packages` and `site-packages` roots, installed npm `package.json` records under the three declared roots, and captures the 12 pinned Go application files. It does not execute image code. Link policy version 2 resolves bounded symlink chains and permits a non-metadata alias only when its final target exists and the target cannot expose unscanned Debian, Python, or npm metadata. Aliases to regular files, aliases to already parsed metadata, and metadata-free directory targets are counted as ignored. Links at guarded roots or ancestors, hardlinks in guarded scopes, aliases to unscanned metadata, and directory targets containing unguarded nested links remain unresolved. Every observed identity must have an exact typed purl in the per-platform SPDX document.

Each pinned Go binary must match the SHA-256 on its exact SPDX `File`, the ELF target, and its `go version -m -json` main module. A direct `command-line-arguments` build is accepted only when its dependency metadata contains exactly one `expected-module`/`(devel)` self record and no other local main module. The gate also requires exactly one matching Go standard-library package. It validates the package-to-file `OTHER` relationships with Syft's exact `evident-by` comment and compares the effective build dependencies with those package records. It reads package relationships per binary, so repeated dependency purls across different binaries are not treated as document-wide ambiguity. Local-build main modules remain `UNKNOWN` in SPDX; their source versions come from the pinned application manifests and are not claims made by the binary's build information.

Both platform receipts and a canonical aggregate predicate are produced. The aggregate requires a schema-exact receipt for each platform and binds the exact run, attempt, engine and workflow revisions, index, child manifests, configs, containers, root filesystems and effective limits, SPDX documents, ignored-link policy, exporter identity, pinned Go tool digest, exact 12 application tuples, scope and limitations. The `https://lyrashieldai.com/attestations/sandbox-sbom-coverage/v1` predicate is signed and verified with the same fixed workflow, revision, source ref, hosted-runner policy, run and attempt used for the other publication attestations. The pre-coverage publication predicate and the final four-predicate coverage set are verified in explicit `publication` and `coverage` phases. The receipts and predicate are uploaded as workflow evidence.

This is **bounded package coverage**, not proof of image-wide SBOM completeness. The current workflow still retains the unconditional promotion hold because an actual hosted run has not completed this gate for both native images. A green local fixture or parser test does not remove that hold.
